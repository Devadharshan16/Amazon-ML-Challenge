### Detailed Pipeline

#### Stage 0 — Data Understanding & Cleaning

- Load all files with `sep="\t"` (critical — commas appear inside address and ID-list fields).
- Normalize text: lowercase, strip punctuation, expand common abbreviations (`corp`↔`corporation`, `pvt`↔`private`, `ltd`↔`limited`, `rd`↔`road`, `st`↔`street`, `&`↔`and`).
- Split address into components where possible (street, area/landmark, city, PIN/ZIP, state) — but keep the raw string too, since components will often be missing or merged.
- Build a **legal-suffix stripped name** field separately (e.g., "Sri Lakshmi Traders" from "Sri Lakshmi Traders Pvt Ltd") — very useful for blocking.
- Treat `country` as a free-form string key, not a fixed category — use it for partitioning/blocking, but don't branch your feature code on `if country == "India"`. Any country-specific normalization (e.g. PIN code regex) should be applied opportunistically (try US ZIP pattern, try Indian PIN pattern, etc.) rather than gated on the country label, so France doesn't fall through a hole.

#### Stage 1 — Blocking / Candidate Generation (recall-focused)

Goal: for each S1 record, generate a manageable candidate set from S2/S3 that almost certainly contains the true matches, while cutting away the vast majority of non-matches. This determines your **recall ceiling** — nothing downstream can recover a true match blocking never proposed.

Common complementary blocking strategies (use several in parallel and union the results):

1. **Country partition** — never compare across countries (huge, safe reduction). Since France appears only in test, this still works fine as a first-level partition — you just won't have training pairs to learn from directly for it (see Stage 3 note below).
2. **Token/n-gram blocking on name** — index records by significant name tokens (excluding stopwords/legal suffixes) or character n-grams (e.g. 3-grams); candidates = records sharing ≥1 token/n-gram with S1's name.
3. **Phonetic blocking** — Soundex/Metaphone/Double Metaphone on business name tokens, to catch spelling variants and transliterations.
4. **TF-IDF + approximate nearest neighbor** — vectorize names (and optionally address) with char n-gram TF-IDF, use cosine similarity + a library like `sklearn` NearestNeighbors or an LSH/MinHash scheme to retrieve top-k nearest S2/S3 records per S1 entity.
5. **Address-based blocking** — block on normalized city + PIN/ZIP (when present) as a secondary signal, since a name might be badly mangled but the PIN code is exact.
6. **Sorted-neighborhood** — sort all records (within country) by normalized name, slide a window, treat co-occurrence in the window as a candidate pair — cheap and catches near-miss alphabetical variants.

Union all candidates per S1 entity, dedupe. This union, _after_ any pruning you do before feeding the matcher, is what goes into `candidate_pairs.tsv` — remember the spec wants your **last** pre-inference candidate set, not the raw union from every blocker if you further filter it.

**Sanity check on training data**: compute _blocking recall_ — of all true (S1, S2/S3) pairs in ground truth, what % appear in your candidate set? This is your ceiling. Iterate on blocking until this is high (aim 97%+) before touching the matcher — you can't out-model a bad blocking recall ceiling.

#### Stage 2 — Feature Engineering (pairwise features, for every candidate pair)

For each (S1 record, candidate record) pair, compute a feature vector:

**Name similarity features:**

- Exact match (normalized), token-set ratio, token-sort ratio
- Levenshtein distance / normalized edit distance
- Jaccard similarity on token sets
- TF-IDF cosine similarity (char n-gram and word n-gram)
- Jaro-Winkler similarity (good for typos)
- Phonetic match flag (Soundex/Metaphone equality)
- Abbreviation-aware match (after suffix stripping/expansion)
- Length difference, common prefix length

**Address similarity features:**

- Same set of string-similarity metrics applied to full normalized address
- Component-level matches where extractable: same city? same PIN/ZIP (exact or fuzzy)? same state?
- Token overlap ratio on address (helps with landmark phrasing, reordering)
- Numeric token overlap (building/house numbers often survive noise well)

**Structural/meta features:**

- Same country flag
- Source pair type (S1-S2 vs S1-S3) — if match patterns differ by source
- Candidate's rank/score from the blocking retrieval stage (e.g. its cosine similarity rank) — a useful prior
- Counts: how many other candidates does this S1 entity have; how many other S1 entities is this S2/S3 record a candidate for (helps down-weight generic/common names like "Star Traders")

#### Stage 3 — Matching Model (precision-focused)

- **Labels**: from `train_ground_truth.tsv`, every (S1, matched_id) pair is a positive; every other candidate pair generated by your blocker for that S1 entity is a negative. This gives you a binary classification training set.
- **Model**: given the constraint (≤8B params, MIT/Apache-2.0 license), you have two broad choices:
    - **Classical ML on engineered features** (gradient boosting — XGBoost/LightGBM/CatBoost, or logistic regression as a baseline) — usually very strong for ER tasks like this, fast, interpretable, and license is a non-issue since it's not even an "LLM."
    - **Small open-weight transformer embeddings** (e.g. a sentence-transformer / small BERT-family model under 8B, Apache/MIT licensed) to generate name+address embeddings, feed cosine similarity as an extra feature, or fine-tune a small cross-encoder for the pair classification itself.
    - A hybrid (GBM on top of both hand features + embedding similarity) tends to perform best in practice.
- **Handling the unseen France in test**: make sure features are _not_ country-value-specific (no one-hot of country as a raw categorical unless you also have an "unknown/other" bucket handled gracefully) — favor same-country-flag, similarity scores, and generic normalization so the model transfers.
- **Calibrate for F₀.₅**: since precision is weighted 2×, tune your decision threshold (don't just use 0.5) on a held-out validation split by directly optimizing macro F₀.₅, not accuracy or F1. Expect the optimal threshold to sit higher than default.
- **Multi-match logic**: since an S1 entity can match multiple S2/S3 records, this is not "pick top-1" — it's per-candidate-pair binary decision (or a ranking + threshold cutoff) allowing 0, 1, or many positives per S1 entity.
- **Singleton handling**: explicitly monitor precision on entities predicted as singleton vs. non-singleton; consider a slightly higher acceptance bar when an S1 entity has only weak/borderline candidates, since a false match on a true singleton costs a full 0 on that entity's F₀.₅.

#### Stage 4 — Post-processing & Output Generation

- Enforce output constraints: one row per S1 test entity (including zero-candidate ones — empty string, not omitted), no duplicate IDs, no cross-source contamination, matched IDs ⊆ candidate IDs.
- Optionally apply light global consistency rules (e.g., if a S2 record is confidently matched to one S1 entity, it's usually — though not always, since duplicates within a noisy source are possible — de-prioritized as a match for another S1 entity) — be careful, since S1 is deduped but S2/S3 aren't necessarily, so many-to-one is legitimate.
- Write `candidate_pairs.tsv` and `matching_results.tsv`, then run `utils/validate_submission.py` locally before every leaderboard upload.

#### Stage 5 — Validation Strategy

- Hold out a slice of `train_source1.tsv` (with its ground truth) as your own validation set — don't peek at it during feature/threshold tuning.
- Compute macro F₀.₅ yourself exactly as the formula specifies, including giving singletons a 1.0/0.0.
- Track **blocking recall ceiling** and **final F₀.₅** separately — they diagnose different failure modes (blocking miss vs. matcher miss).

A few things worth flagging as you start:

- **Build the validation split first**, before writing a line of model code — carve it out of `train_source1.tsv` + ground truth and hold it untouched, since every threshold/feature decision needs to be judged against your own F₀.₅, not the leaderboard.
- **Blocking recall is your ceiling** — measure it explicitly (what fraction of true pairs survive into your candidate set) before tuning the matcher. A common mistake is spending all your time on model tuning while blocking silently caps you at 85% recall.
- **The France-in-test-only detail is a trap for hardcoded country logic** — anything that special-cases `if country == "US"` or `"India"` instead of applying normalization heuristically will silently fail on French addresses.
- **Threshold tuning is not optional** — the default 0.5 cutoff on your classifier is very unlikely to be F₀.₅-optimal; sweep it against your validation split.
